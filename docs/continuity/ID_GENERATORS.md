# ID generators — who generates which identifier

Every link in the causal chain carries an identifier. The rule for all of them: **generated, never typed.**
A typed ID once collided with another executor's (two bridge blocks with the same number, 24/09/2026).

Two generators cover everything:

| Generator | IDs |
|---|---|
| [`tools/generate-ids.js`](../../tools/generate-ids.js) | `WORION-<TYPE>-<YYYYMMDD>-<HHMMSS>-<purpose>` for every type below; Sao Paulo clock; with `--repo`, never reuses an ID already in the repository |
| [`tools/generate-publication-ids.js`](../../tools/generate-publication-ids.js) | the publication pair: `PAIR_KEY`, `PROV-NOTION-<key>`, `PROV-GITHUB-<key>` |

## Who generates which

| ID | Generated by | Carried by / preserved by |
|---|---|---|
| `PROMPT_ID` of a prompt | **the prompt generator** (the AI that writes the prompt with the human) — it goes in the prompt header | the executor **preserves** it and answers with `RESPONSE_TO_PROMPT_ID` equal to it; it never generates another |
| `PROMPT_ID` of a direct order | the **executor**, when the human orders directly, with no prompt | the executor, in every commit, bridge block and report of that cause |
| `COMMAND_ID` | the executor, when the flow tracks the order separately | the prompt header (`COMMAND_ID DE ORIGEM`) |
| `EXECUTION_ID` | the executor, one per run | commit messages; `PARENT_EXECUTION_ID` when another executor continues |
| `RESPONSE_ID`, `ARTIFACT_ID` | the executor | the reply / the artifact |
| `BLUEPRINT_ID` | the executor, when it opens a job | the job's blueprint file, the bridge, the governor's decisions |
| `REVIEW_ID` + its `EVENT_ID` | the executor, one pair per review point (start, change, end) | the blueprint's `pedidos_de_revisao`; the governor binds its attestation to the `REVIEW_ID` |
| `EVENT_ID` of a mailbox message | the mailbox sender script, automatically | the message file and its receipt |
| `DEEP_ATT` (attestation) | **the governor** (DeepSeek), for each decision | the blueprint's `deep_att`: `review_id`, the governor's own `PROMPT_ID`, `input_sha256`, decision, model, time |
| `ENTRY_ID` | the governor, when the human delivers a file — or brought by the human | every prompt, commit and transcript that uses that file |
| `ID_PONTE` | the first executor of the day | the daily bridge header |
| `PAIR_KEY`, `PROV-GITHUB-…`, `PROV-NOTION-…` | whoever publishes the pair: a commit's pair by the provenance governor, a human delivery's pair by the Notion ↔ GitHub organizer | both destinations, byte-identical, with read-back |

## How the chain closes

```text
human order / ENTRY_ID
→ PROMPT_ID (generator)            → preserved by the executor
→ BLUEPRINT_ID + REVIEW_ID (executor)
→ DEEP_ATT PERMIT (governor)       → bound to the REVIEW_ID
→ commits with PROMPT_ID and EXECUTION_ID
→ RESPONSE_TO_PROMPT_ID = PROMPT_ID
→ PAIR_KEY (publication)
```

A missing link is reported as `ELO_AUSENTE` (missing link), never filled by inference.

## A correction this page records

Until 25/09/2026 the executors' rules said the executor generated the `PROMPT_ID` and the prompt generator
produced a separate `ID_PROMPT`. That contradicted the canonical provenance contract and was corrected: the
`PROMPT_ID` belongs to the prompt generator; the executor preserves it. Older prompts named `WORION-ID-PROMPT-…`
are history and are not renamed.

Source repository: `leedermix-arch/worion-desktop`, branch `canonical/worion`
(`scripts/generate-prompt-id.js`, `scripts/generate-update-ids.js`, commit `75aa5191` for the correction).
